01 · Codex 体验文章：沿着一个任务写#

作者与来源： Janine Heinrichs，Unite.AI，2026-05-28。原文：OpenAI Codex Review。

作者做了什么。 她以制作产品落地页为任务，按步骤记录项目创建、计划、执行和成果检查，并配上过程截图。这是个人体验；网站披露了推广链接，不是对照用户实验。

可以学的写法： 任务背景 → 实际步骤 → 关键状态截图 → 体验评价。本站可以进一步问：用户选对项目和模式了吗，能找到结果吗？一张菜单图不证明授权机制有效，文中的速度也不能当作普遍性能。

02 · Copilot 用户研究：从行为归纳模式#

作者与来源： Shraddha Barke、Michael B. James、Nadia Polikarpova，Grounded Copilot，OOPSLA 2023。作者公开的论文 · DOI。

研究结论摘要： 研究观察了 20 位参与者，归纳出“加速”和“探索”两种交互模式：有明确思路时用 AI 补全；不知道下一步时用它找方向。研究对象是当时的 GitHub Copilot。

可以学的写法： 先写观察方法，再从反复出现的行为形成解释，最后谈设计启发。对 Codex 可以提出一个延伸问题：明确任务和探索任务，是否需要不同程度的计划与解释？这是待验证的迁移，不是论文已经测试了 Codex 桌面端。

03 · RECAP：把聊天与代码变化放回同一条时间线#

作者与来源： Keyu He、Qianou Ma、Valerie Chen、Wayne Chi、Tongshuang Wu，RECAP，arXiv v1，2026-05-01。论文正文与原图。

研究做了什么。 这个研究工具把聊天和代码记录联起来，在大学课程中收集了 41 位学生的记录，其中 29 位有聊天数据。它适用于 VS Code / Copilot；是预印本中的系统展示，不能当作 Codex 与 Claude 的比较实验。

可以学的写法： 解释要回答的问题，再用系统图或界面图说明证据怎样记录。本站可以借鉴它的记录方式，把“提出需求、修改文件、检查结果”关联起来，而不是只留最后一个成功页面。

04 · Claude Code 会话研究：先解释数据，再读图#

作者与来源： Anthropic 研究团队，Agentic coding and persistent returns to expertise，2026-06-16。原始报告。

研究结论摘要： 报告分析约 40 万次 Claude Code 会话，涵盖 CLI、网页与桌面渠道。典型分工是人决定目标、Claude 决定执行；结论来自对日志的分类器判断，并非 Cowork 的按钮可用性实验。

可以学的写法： 数据范围 → 指标定义 → 图表 → 局限。对 Cowork 可提出一个问题：委托执行时，人的目标和检查节点是否仍然清楚？厂商数据可以启发问题，但其相关性结果不能证明某种布局更好。

05 · 设计团队体验：把过程和失败也写出来#

作者与来源： Tom Moran、Dan Bradshaw，Valliance，2026-04-21。原文：Claude Design collaborative test drive。

作者做了什么。 两位设计师各用约 90 分钟探索资料库界面，记录不同的起步方式、迭代与阻力。他们肯定直接在画面上提修改的方式，也讨论聊天信息混杂的问题。这是团队个案，研究的是浏览器中的 Claude Design。

可以学的写法： 共同任务 → 不同做法 → 具体阻力 → 改进方向。本站可以沿用这个结构记录反馈是否明确、结果如何恢复；两位作者的经验不能代表所有用户，4 月界面也不能称为今天的最新版。

给这个博客的写作模板#

选读文章可以使用：问题 → 原作者与方法 → 配图 → 简明结论 → 适用范围 → 本站的延伸问题。如果后来有自己的实测，再补任务、平台、人数、记录和结果。

  • 资料调研： 阅读与归纳已有研究，不要求我先做一轮实验。
  • 界面解读： 指着有来源的截图解释设计，判断与事实分开。
  • 亲自观察： 用自己的任务和截图记录过程，写明实际体验。

三种文章都可以留在交互观察里。正式论文、厂商研究和个人体验各有用途；先看作者怎样取得证据，再决定结论能支持多大的判断。
