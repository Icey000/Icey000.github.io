Executed on 8 November 2026. I built a new Unity 6 project, trained a robot with reinforcement learning (PPO, Unity ML-Agents 4.1.0) on my laptop CPU, and evaluated the exported model inside a playable Windows build against a hand-written baseline. All numbers and screenshots below come from those runs.

What the assignment asks — and what I chose#

Page 166 of the HCI lecture handout asks for “your first larger Unity Application using ML agent” and a blog that documents the process. Roll-a-ball is offered as one example, not a requirement. ML means machine learning; the page does not demand multiple agents or a particular algorithm.

I did not want a ball that learns to touch a cube. Since this is an HCI course, I designed the agent around a human giving it instructions:

A blackout has hit a station. The human tells the rescue robot which power cell to fetch (blue or orange). The robot must find that cell, ignore the wrong one, cross an area with cables that discharge periodically, and deliver the cell to the generator.

The requested cell is an input to the policy (a goal-conditioned agent). That makes the same trained network controllable by a person now, and by a natural-language interface later.

Setup#

Python3.10.12 in a separate conda environment, PyTorch 2.2.2 CPU build
HardwareAMD Ryzen 7 8845H, integrated Radeon 780M, no CUDA GPU
Training4 headless game instances × 16 arenas = 64 robots learning in parallel

No discrete GPU turned out to be fine: the robot perceives the world through numbers and rays, not camera images, so PPO trains at roughly 2,000 steps per second on the CPU.

Designing the agent#

What it observes (25 numbers + 136 ray values)

  • which cell is requested (one-hot) and which cell it carries;
  • the relative position of both cells and of the generator;
  • its own velocity and whether it is stunned;
  • for each cable: relative position, orientation, live or not, and time until it switches;
  • a 360° ray sensor that tags walls, cells, generator and live/dead cables.

What it does: two continuous actions — move left/right and forward/back.

Rewards

EventReward
Deliver the requested cell to the generator+1.0 (episode ends)
Pick up the requested cell (first time)+0.2
Touch the wrong cell (rejected, not picked up)−0.2 once
Get shocked by a live cable (drops cell, 1.5 s stun)−1.0
Getting closer to the current sub-goal+0.1 per metre
Time−0.5 spread over the 40 s limit

Curriculum: lesson 1 has no cables; once the average reward passes a threshold, lesson 2 adds one cable and lesson 3 adds the second.

The process: four attempts, three real problems#

Toolchain problems (solved in minutes, but worth writing down)#

  1. “No valid Unity Editor license found” in batch mode. The licence client needs an access token from Unity Hub. Hub was not running; starting it fixed batch builds.
  2. ModuleNotFoundError: pkg_resources. mlagents 1.1.0 still imports pkg_resources, which recent setuptools removed. Pinning setuptools<70 fixed it.
  3. The option ﻿behaviors … is invalid. PowerShell’s Set-Content -Encoding utf8 wrote a byte-order mark at the start of the YAML file. Rewriting it as UTF-8 without BOM fixed it.

v1 — stuck at 8 % success#

After 400k steps the robot succeeded in only ~8 % of episodes. Looking at the statistics, wrong installs were as frequent as correct ones: if the robot grabbed the wrong cell it could never put it down, so the rest of the episode was a dead end that taught it nothing. Fix: the wrong cell is now rejected on contact with a penalty, and the progress reward was made five times stronger.

v2 — 97 % success, but it never learned to avoid cables#

v2 learned quickly. Then I evaluated the exported model over 200 episodes against a scripted baseline that simply drives straight at its goal:

v2 evaluation (2 cables)SuccessMean timeShocks / episode
Trained PPO (v2)97.5 %6.0 s1.00
Scripted straight line99.5 %4.0 s1.13

The learned policy was shocked as often as a controller that ignores cables. Two reasons: a shock cost only −0.3 and a 1 s stun, so ploughing through was cheaper than detouring; and the robot had no information about when a cable would be live. Without the baseline comparison I would have reported “97 % success” and missed this completely.

Fix (v3): shock penalty −1.0 with a 1.5 s stun, and each cable’s position, orientation, live state and time-to-switch added to the observations.

v3 — learns to avoid live cables#

The curve shows the curriculum at work: when the first cable appears (1.04 M steps) shocks jump to about six per episode and success drops, then the robot learns to cross safely. Training took 36 minutes for 4 M steps.

Evaluated in the build, v3 was shocked far less than the baseline (0.42 vs 1.51 per episode) but succeeded only 92 % of the time: 8 % of episodes timed out while it hesitated near cables. Its curriculum had spent only 2.4 M steps on the full two-cable task.

v3 fine-tuned — the final model#

I continued from the v3 weights for 2 M more steps on the two-cable task only, with a lower learning rate (1.5e-4) and less exploration (entropy 3e-3). This took 18 minutes and removed most of the timeouts.

Results#

Evaluation runs the exported ONNX model inside the Windows build — not training statistics — for 300 random layouts with both cables active.

PolicySuccessMean time when successfulShocks / episodeTouched wrong cell
Trained PPO (v3 fine-tuned, final)97.3 %6.2 s0.3312.7 %
Trained PPO (v3)92.0 %7.4 s0.4212.7 %
Scripted straight line97.3 %4.3 s1.513.3 %

The final learned robot matches the scripted baseline’s success rate while being shocked 78 % less often. It is about two seconds slower: waiting for a cable to switch off costs time. It also brushes the wrong cell more often (12.7 %), because it is rewarded for avoiding cables, not for keeping a wide berth around the other cell.

Playing with it: human commands#

In the play build the human presses 1 (blue) or 2 (orange) at any time. The robot drops a cell that no longer matches and re-plans immediately — the same trained network, now taking instructions from a person.

The visuals are deliberately simple primitives with URP bloom and emergency lighting; the effort went into the learning problem.

What I would tell someone following this path#

  • Always evaluate against a dumb baseline. My most important finding (v2 did not avoid cables) was invisible in the training curve.
  • Look for dead-end states when learning stalls. One irreversible mistake can waste most of your training data.
  • Give the agent the information it needs to act well. It cannot time a crossing it cannot perceive.
  • Penalties must outweigh the shortcut. If cheating is cheaper, PPO will find it.
  • You do not need a GPU for vector/ray observations; run several headless builds in parallel instead.

Limitations and next steps#

  • The evaluation uses one random seed per policy and 300 layouts; I have not yet repeated training with different seeds, so the numbers show one run, not a distribution.
  • Commands are keys today. Next: a natural-language layer where a language model turns “grab the blue battery” into the goal the policy already understands.
  • Then human–AI teamwork: tasks that need two players (one holds a switch while the other passes), and a small user test comparing a scripted teammate with the learned one.

Reproduce#

Evaluation: TeamRescueDemo.exe -eval 300 eval.json (add -baseline for the scripted controller). Interactive play: run TeamRescueDemo.exe, press 1 / 2 / R.
